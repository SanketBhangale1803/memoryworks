# T-002: Self-observability. MemoryWorks's own failures become signals

- **Status:** open, depends on T-001
- **Pillar:** Dogfood (`VISION.md` §2)

## Problem
MemoryWorks already *knows* when it fails, but only in operational tables nobody asks:
- `background_jobs.status/error` (`backend/app/jobs.py`, `_finish` at about line 119, `requeue_stale` at about line 129)
- `connector_sync_jobs.last_error` and `ingestion_jobs.error` (read by `backend/app/connectors/status.py`)
- OAuth outcomes (`connector_auth_outcomes` in `connectors/status.py`)
- LLM caps and timeouts (`backend/app/llm/`, `test_llm_limits.py`)

`connectors/status.py` already shows the right pattern: it answers connection questions from live records rather than from memory. T-002 generalizes that pattern into T-001 signals.

## Outcome
Each failure class emits a T-001 Signal at the moment it happens, with `source="memoryworks"`, fingerprinted so that 50 failed Drive imports become **one** Issue with `occurrences=50`, plus the latest error text with secrets redacted. A later success for the same fingerprint resolves it.

## Constraints
- Emitting a signal must never make the original operation fail. Wrap it, log it, and move on.
- Error text passes through redaction. Tokens, emails in URLs, and query strings never reach a signal.
- A signal is scoped to the workspace that owns the job.

## Acceptance
- Tests: a failing job, a failing sync, and a failing OAuth callback each produce one Issue. Repeated failures increment `occurrences`. A success resolves the Issue. Redaction strips a token-shaped string.
- CI is green.
