# T-001: Signal and Issue model, plus GitHub CI and PR-state signals

- **Status:** open (authoritative copy in `STATUS.md`)
- **Pillar:** Situation (`VISION.md` §1)
- **Planner output:** `orchestration/plans/T-001/PLAN.md`, `SKILLS.md`

## Problem
MemoryWorks stores memory, but it has no record of what is true *right now*. The GitHub connector (`backend/app/connectors/github/client.py`, `sync()` at about line 136) reads commits, files, issues, and PRs. It never reads check runs, workflow runs, deployments, or PR review state. So "what's failing in CI?" has no data behind it.

## Outcome
1. A persisted **Signal**: an observation with a `source`, `kind` (e.g. `ci_failure`, `deploy`, `pr_stalled`, `sync_error`), `subject` (repo/service/connector), `severity`, `observed_at`, `expires_at`, `evidence_url`, `fingerprint`, workspace and project scope, and team grants inherited from the source.
2. An **Issue**: open signals clustered by fingerprint into one open problem, with `first_seen`, `last_seen`, `occurrences`, `status` (`open`, `resolved`, or `muted`), `owner` (resolved the same way `orgops/service.py:get_owner` resolves owners), and links to related memories (incidents, decisions) found through existing memory search.
3. GitHub produces signals for: failed or cancelled check runs and workflow runs on the default branch and on open PRs; PRs open for more than N days with no review; and failed deployments, if the Deployments API returns any. These come from both polling sync and the existing webhook path (`api/routes.py` `_process_github_webhook_event`, about line 1119).
4. A newer success for the same fingerprint resolves the Issue automatically.

## Constraints
- Team scoping must work as it does for memory. A signal is never broader than its source (`governance/`).
- No LLM runs in signal or issue creation. It has to be deterministic.
- Signals don't become memories. An Issue can *link* memories and can be *promoted* into an incident memory only through the existing proposal and approval flow.
- Storage goes in SQLite through `app/core/database.py`, following existing DDL patterns. No new infrastructure.

## Acceptance
- Unit tests: fingerprint clustering, auto-resolve on success, expiry, and team trimming.
- An integration test with recorded GitHub API fixtures (no network) shows a red workflow run becoming an open Issue, and a later green run resolving it.
- `ruff`, `black --check`, and `pytest` pass.

## Planner: decide in PLAN.md
Table shapes and indexes. The fingerprint formula. How sync cursors cover check runs without blowing the GitHub rate limit. Webhook event types to subscribe to. Whether `Issue` needs its own table or is a view.
